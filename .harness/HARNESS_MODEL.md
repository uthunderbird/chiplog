# Модель харнесса Chiplog

Это локальный исполняемый адаптер общей модели из публичного проекта
[`harness-boilerplate`](https://github.com/uthunderbird/harness-boilerplate).

- Нормативная upstream-база: [`6a306d23`](https://github.com/uthunderbird/harness-boilerplate/blob/6a306d23d3ac560620fe723b90569ea1dd545748/HARNESS_MODEL.md).
- [Текущий `master`](https://github.com/uthunderbird/harness-boilerplate/blob/master/HARNESS_MODEL.md) — только справка: он не меняет правила Chiplog без отдельного коммита.
- Объяснения и примеры живут upstream; здесь остаётся всё, что надо исполнить офлайн, локальные отличия, инварианты и долги.

При расхождении модели с репозиторием код — факт, документ — описание. Зафиксируй расхождение:
модель меняется только через ретро и с разрешения человека; спор о норме запиши через `decide.sh`.

## Локальные отличия

- `AGENTS.md` — событийный реестр ежедневных инструкций; правило-файл без проверки до агента не доставляется.
- Перед коммитом выполняется один холодный `$swarm-red-team` только по P0/P1, а не `/polish`.
- Долги ниже принадлежат Chiplog. Upstream-долги сюда автоматически не переходят.
- Путь этой модели — `.harness/HARNESS_MODEL.md`; активные инструменты обязаны ссылаться на него явно.

## С чего начать

У тебя провал. Маршрут ниже выбирает артефакт; порядок шагов обязателен.

1. **Это мета-правило о харнессе?** Да → разбери на ретро; отдельной формы хранения такого провала нет. Нет → дальше.
2. **Есть наблюдаемый предикат над репозиторием?**
   - да → правило-файл через `./.harness/scripts/new-rule.sh`, затем вопросы 0–4;
   - да, но вход — воспроизведение работы агента → то же с `kind: agent`, затем `new-case.sh`;
   - нет, норма только о процессе → раздел `AGENTS.md`, затем вопрос 2: проверка или `[без гейта]`.
3. **Чем обоснован класс ошибки?**
   - падающий вход → правило-файл рождается сразу;
   - вход построить не удалось → запись в `.harness/observations.md`, правило пока не рождается;
   - норма установлена словом человека → `norm: true` и `reviewed`; агент эту ветку сам не выбирает.
4. **Где дом класса?** Воспроизводится в проекте с другим стеком → общий навык агента; иначе → Chiplog.
5. **Какова ширина?** Бери самый широкий класс, для которого построенный вход всё ещё падает.

«Входа нет» означает «пытался построить и не смог». Разовый шум без входа правилом не закрывается.
Дешёвые ветки всегда оставляют обоснование: мета-правило — в ретро, процесс без гейта — рядом
с `[без гейта]`, наблюдение — строкой в `observations.md`. Самоотчёт без следа ветку не закрывает.
`new-rule.sh` создаёт заготовку; обязательные `kind`, `norm` и `reviewed` при нужной ветке дописываются руками.

## Пять вопросов о правиле

Вопросы 0–4 относятся к правилу-файлу. Для раздела `AGENTS.md` достаточно вопроса 2.

### 0. Где хранится провал?

- Обычный вход: непустой `.harness/reproducers/<id>/`, подключённый к `test.sh`.
- `kind: agent`: `case.md` с дословными репликами, состоянием мира и прежним харнессом; процедура — в `reproducers/README.md`.
- Норма человека может не иметь входа. Наблюдение без входа остаётся в `observations.md`.

Результат: вход существует, падает без правила и проходит с ним; правило и вход коммитятся вместе.

### 1. Из чего состоит правило?

Правило несёт формулировку, `error_class`, дешёвый обход и обоснование: вход либо `norm: true`
с `reviewed`. Для поведения агента добавляется `kind: agent`. Канонические обходы — в `AGENTS.md` §4.

Результат: правило описывает класс следующей ошибки, а не единственный случай.

### 2. Где живёт проверка?

- Время жизни: цель сессии → `AGENTS.md` → исполняемая проверка.
- Модальность: суждение может говорить через хайлайт `→ реши:`, но не блокировать; механический предикат может держать.
- Момент: вход в сессию — `dashboard.sh`; перед ходом — `healthcheck.sh`/`guard-edit.sh`; коммит — `gate.sh`; ретро — `retro/TEMPLATE.md`.
- Проверка в `checks/` считается подключённой только после строки `run` в `gate.sh` или вызова из `healthcheck.sh`.

Если нарушение может не дойти до коммита, говори раньше. Проверка дороже вреда → не поднимай её до скрипта.

### 3. Что говорит проверка при провале?

Ровно одна метка на сообщение:

| Метка | Владелец и действие |
|---|---|
| `→ команда:` | агент исполняет полностью заданную строку; `✓` запрещён |
| `→ сделай:` | агент производит содержательный результат; `✓` обязателен |
| `→ реши:` | агент выясняет и пишет выбор через `decide.sh`; `✓` обязателен |
| `→ стоп:` | решает человек; названы обе неразрешимые чтением ветки и `✓` |
| `→ чинить нечем:` | чинится названная часть проверки, а не работа; `✓` обязателен |

`✗` называет проявившийся дешёвый обход. Код статически держит метку, правила `✓` и `decide.sh`;
уместность `✗` и содержательность веток остаются соглашением.

### 4. Чем проверяется сама проверка?

Для каждого `run` в `gate.sh --self-test` есть плохой вход, который роняет проверку, и хороший,
который проходит. Проверяется наблюдаемый исход, не внутренняя реализация. Если дешёвого самотеста
нет, сообщение говорит `→ чинить нечем:` и называет непроверяемый кусок.

## Жизненный цикл

- Рождение: падающий вход либо норма человека.
- Усиление: текст → хайлайт → блокировка, только пока стоимость проверки оправдана.
- Ослабление: дорогая проверка снимается, правило может остаться текстом или записью ретро.
- Удаление: удали правило и прогони его вход; гейт всё равно ловит → удаляй, ошибка вернулась → верни.
- Изменение `error_class` обнуляет `reviewed`: прежняя ревизия не легитимирует новый класс нормы.
- Идентификаторы правил и долгов не переиспользуются.

## Соглашения

Гейт не доказывает, что вход действительно прогнан и падает, `error_class` достаточно широк,
`✗` уместен, cold review действительно был холодным или суждение верно. Эти границы проверяет
ретро. Правило без исполняемой проверки легально: оно служит записью для ретро, не инструкцией агенту.

## Инварианты модели

| # | Инвариант | Вердикт устанавливает | Принуждает |
|---|---|---|---|
| 1 | У каждого правила-файла есть непустой вход либо непросроченная норма | `rules_have_reproducers.py` | он же |
| 2 | У каждого раздела `AGENTS.md` есть проверка либо `[без гейта]` | ретро | никто |
| 3 | Для каждой проверки `gate.sh` есть плохая и хорошая ветки `--self-test` | `gate.sh --self-test` | он же, вручную |
| 4 | Каждое сообщение провала называет действие и владельца | `messages_are_actionable.py` | он же |
| 5 | Из `gate.sh` не исчез `run` без ретро с `outcome: change` | ретро по `git log -p` | никто |
| 6 | Ни один порог не существует в двух местах исполняемого кода | ретро | никто |

При нуле правил инвариант 1 истинен пусто: на ретро пиши «нечего проверять», не «держится».
Порог — число в условии, влияющем на исход или модальность; лимит отображения порогом не является.

## Про сам этот файл

Владелец модели — человек. `decide.sh` фиксирует выбор внутри модели, но не меняет её; изменение
модели проходит через ретро. Закрытый долг удаляется из таблицы, его номер не переиспользуется.
