# Транскрипты

Транскрипт — версионируемый Markdown-сценарий взаимодействия с Chiplog. Он хранит
диалог, исходные условия, вызовы, ожидаемые результаты и проверки состояния.
Реплики читаются как разговор; технические данные находятся возле соответствующего
шага. Авторский сценарий не является свидетельством состоявшегося исполнения.

## Один исходник, отдельный результат запуска

Markdown — единственный редактируемый источник. Реплика или значение записывается
один раз; остальные части ссылаются на него по ID. HTML-комментарии для контрактов
не используются. Полные envelopes и provenance можно убрать в `<details>`, но
вызовы, их результаты и краткие проверки состояния остаются видимыми.

Фактический прогон сохраняется отдельно: inputs, model responses, calls/results,
screens, effects, trace, expected/actual и причины несовпадения. Отчёт связывается
с ID, версией и digest исходника и bundle. Он не переписывает ожидания сценария.

## Паспорт и статус

Каждый сценарий начинается с назначения, статуса и блока `scenario`:

- `format_version: 2` — Markdown-контейнер с именованными репликами и YAML-блоками;
- `id` — стабильное имя истории, `version` — версия её содержания;
- `status: design` — проектируемый сценарий, ещё не исполняемый контракт;
- `status: executable` — сценарий поддерживается конкретным runner и bindings.

Статус executable не означает PASS, успешную работу настоящей LLM или разрешение
на внешние действия. Для каждого из этих утверждений нужно своё свидетельство.
Данные для переиспользования могут иметь `kind: library` в stateful-профиле;
библиотека сама по себе не является сценарием.

## Блоки и реплики

Контрактный блок открывается строкой ` ```yaml transcript ` (без пробелов по краям)
и закрывается ` ``` `. Внутри ровно один discriminator:

| Блок | Назначение |
|---|---|
| `scenario` | Паспорт, исходное состояние, внешние фикстуры, допустимые исходы |
| `step` | ID шага, точный вход и наблюдение, завершающее шаг |
| `design` | Пояснение механики; само по себе не создаёт исполняемой проверки |
| `expect` | Ожидания для явно указанного шага |
| `forbid` | Запреты с определённой областью действия |

Канонические реплики имеют строгую однострочную форму:

```text
**Пользователь · request:** Добавь плавание в планы.
**Chiplog · proposal · пример:** Добавить еженедельное плавание?
**Пользователь · accept:** Да, добавь.
**Chiplog · receipt · exact:** <точный текст контрактного ответа>
```

ID уникален в файле. Текст после маркера — исходные bytes реплики в UTF-8
без перевода строки; внутри реплики нет скрытого второго текста. `message_ref`
выбирает реплику по ID. `$message.request` подставляет её текст в поле данных.
Обычный поясняющий текст и примеры в code fences не являются inputs.

Реплики пользователя служат входами. `пример` у Chiplog задаёт желаемую речь;
проверяется отдельный смысловой контракт, а не совпадение слов. `exact` используется
только там, где конкретный текст — часть контракта; `expect.response.exact` ссылается
на него через `$message.<id>`. Не нужно дублировать ответ внутри YAML.
Непривязанный пример меняет source digest, но не executable bundle digest.

## Локальный шаг

Порядок чтения: реплика или техническое действие → `step` → вызов и результат →
ответ → `expect`. Ожидания связаны с шагом через `expect.step`, а не близостью текста.
Определение шага находится возле его действия, не в длинном списке в начале файла.

````markdown
**Пользователь · request:** Добавь плавание в планы.

```yaml transcript
step:
  id: request
  input:
    kind: message
    message_ref: request
  end: proposal.displayed
```

**Проектируемый вызов → предложение записи.**

```yaml transcript
design:
  tool_call:
    boundary: model_tool
    operation: propose_planning
    arguments:
      text: Плавать каждую неделю
  tool_result:
    source: real_boundary
    type: ToolOutcome
    capture:
      proposal: proposal_id
  rationale: proposal does not commit the plan
```

**Chiplog · proposal · пример:** Добавить еженедельное плавание?

```yaml transcript
expect:
  step: request
  state:
    planning_changed:
      eq: false
```
````

Этот фрагмент показывает устройство шага, а не полный исполняемый сценарий.
Вызов внутри `design` — описание. Для исполнения его проверка должна быть
зарегистрирована в driver либо выражена через поддерживаемый `expect.calls`.

Подтверждение — отдельный input `authenticated_adoption`. В нём связаны реальный
показ, authenticated principal/peer и акт подтверждения. Человеческое «да» не
заменяет эти данные и не заставляет пользователя произносить служебные поля.

## Мир, контекст, фикстуры и результаты

`arrange` задаёт мир до сценария. Контекст модели — отдельная проекция этого мира:
данные, которые модель действительно видит. Наличие значения в arrange или expect
не означает, что оно доступно модели. Stateful-профиль описывает эту проекцию через
`initial_context` и обновления на шагах.

Фикстура содержит boundary, matcher и возвращаемый ответ. Она срабатывает только
на реальный совпавший запрос, сама не вызывает инструмент и не доказывает вызов.
Model fixture подменяет модель; provider fixture подменяет внешний ответ. Фикстура
не может выдавать готовый verdict или подменять внутренний commit.

У результата явно различаются:

- `source: fixture` / `fixture` — ответ объявленной внешней или model boundary;
- `source: real_boundary` — ожидается результат настоящего обработчика при запуске;
- фактически наблюдённый результат — только в отдельном отчёте запуска.

Captures сохраняют реальные возвращённые ID, digest и объекты. Фиксированные
примеры ID не выдают за owner-allocated identity. Все runnable operation names,
аргументы и поля должны иметь точную привязку к versioned API/schema. Символические
проектируемые bindings помечаются как неподключённые.

## Состояние и проверки

Состояние записано структурированно и единожды. Для выбранного observation path
используется один оператор: `eq` — точное значение; `delta` — изменение количества;
`unchanged` — сравнение полного значения с baseline. Количество коллекции должно
быть явно определено её observer binding, а не угадываться по типу операнда.

У шага есть наблюдаемая граница `end`. Stateful-профиль дополнительно задаёт baseline,
causal relations и отдельную изоляцию вариантов. Недостигнутая граница не даёт PASS.
Смысловые проверки речи отделены от детерминированных проверок вызовов и состояния.
Неподдерживаемый predicate/binding означает отказ компиляции или NOT_RUNNABLE,
а не успешную проверку. Отсутствие записи нельзя доказывать только неизменным экраном.

Короткие общие данные можно вынести в библиотеку; последовательность разговора,
входы и наблюдаемые исходы остаются в сценарии. Ошибочная ветка имеет свой шаг/вариант
и явно показывает отказ, неопределённость или отсутствие изменений.

## Поддержка в коде

`verification.transcripts` поддерживает HTML v1 для совместимости, базовый
fenced-формат v2 и stateful-профиль v2. Смешивать скрытые и fenced-контракты нельзя.
Новый YAML decoder поддерживает вложенные списки, block/flow maps, строки,
числа, boolean и null. Дубли ключей, anchors/aliases, нестандартные теги и нечисловые
значения вроде NaN отвергаются. Старый HTML decoder сохраняет прежний YAML subset.

Compiler сохраняет последовательность шагов, связанные реплики и predicates.
Stateful-компиляция раскрывает локальные imports, объединяет непересекающиеся
expectations шага, строит каждый вариант и зависимости событий, проверяет captures
и точку остановки prefix. Изменение контракта общего файла меняет bundle digest
потребителей. Библиотека компилируется отдельно, но не выдаётся за прогон сценария.

Структура boundary payload не подменяет production schema: точные поля аргументов,
результатов и observations проверяются зарегистрированным runtime binding.
Наличие синтаксически допустимого поля или capture ещё не доказывает исполнимость.

`verification.loop_scenario` продолжает исполнять зарегистрированный
[local-planning-receipt](transcripts/local-planning-receipt.md) через настоящий
production loop. Он проверяет canonical input, порядок шагов, состояние до
подтверждения и итоговый receipt. Неподдерживаемый контракт не получает PASS.

Общий запуск одного файла или каталога:

```sh
uv run python -m chiplog.verification.transcript_suite design-docs/transcripts \
  --artifact .artifacts/transcripts/result.json
```

Файл отчёта должен быть новым; существующий результат не перезаписывается.
Отчёт содержит результат компиляции, source/bundle digests, зависимости и результат
каждого сценария/варианта. Для исполняемого локального сценария включены реальные
records, display и receipt; для остальных перечислены отсутствующие bindings.

| Статус | Значение |
|---|---|
| `PASS` | Зарегистрированный сценарий реально исполнен, проверки прошли |
| `COMPILED` | Библиотека успешно разобрана; самостоятельного прогона нет |
| `NOT_RUNNABLE` | Формат поддерживается, но runtime/bindings ещё отсутствуют |
| `FAIL` | Ошибка компиляции или нарушение исполняемого контракта |

Код выхода: 0 для PASS/COMPILED, 2 для NOT_RUNNABLE, 1 для FAIL.
Общий статус каталога не скрывает неподключённые варианты за успехом одного
сценария. В текущем дереве локальный R13 исполняется; календарные, журнальные
и stateful-сценарии получают NOT_RUNNABLE. Это поддержка формата, а не имитация
недостающего поведения продукта.

[Stateful-профиль R13](transcripts/drafts/r13/STATEFUL-PROTOCOL.md) задаёт
`protocol_version: 2` независимо от Markdown `format_version`. Его compile path
подключён; production runner, часть ToolSpecs и observer/fault bindings пока нет.
Статус design у этих сценариев сохраняется.

План расширения: [матрица R14–R17 и детализация календарных историй](R14-R17-TRANSCRIPT-PLAN.md).
В нём готовность механизмов отделена от сквозной интеграции T01 в R18.

- [Пропущенное занятие](transcripts/fact-claim-without-plan-change.md) — design; запись сообщения пользователя без изменения плана.

- [Локальная запись в планы](transcripts/local-planning-receipt.md) — executable hermetic; текущий production loop.
- [Набор R13](transcripts/drafts/r13/STATEFUL-PROTOCOL.md#набор) — design; история, подтверждение, replay, completion и workspace.

Набор R14–R17 использует тот же stateful-профиль. T01 и T03 выше сохраняют свои
ID и имеют version 3: отдельные варианты подтверждения, replay, crash, неизвестного
исхода и восстановления. [Общие календарные данные](transcripts/drafts/r14-r17/common.md)
объявляют неподключённые bindings. Полный T01 требует интеграции R18.

- [P03: прерванное выполнение](transcripts/drafts/r14-r17/03-call-recovery.md).
- [P04: потерянный ответ модели](transcripts/drafts/r14-r17/04-model-response.md).
- [P05: срабатывания расписания](transcripts/drafts/r14-r17/05-scheduler.md).
- [P06: смена исполнителя](transcripts/drafts/r14-r17/06-takeover.md).
- [P07: приём сообщения при сбое](transcripts/drafts/r14-r17/07-ingress.md).
- [P08: доставка готового результата](transcripts/drafts/r14-r17/08-delivery.md).

P03–P08 — компонентные истории с [общими наблюдателями и настройками](transcripts/drafts/r14-r17/mechanisms-common.md).
Они задают детерминированные проверки механизмов, но не доказывают прохождение
пользовательского диалога production loop. Все новые варианты имеют status design
и при текущем запуске должны давать NOT_RUNNABLE с причинами; COMPILED относится
только к библиотекам. Внутренние результаты обязаны поступить с реальных границ.

Изменение inputs, fixtures, проверок или их связей повышает версию сценария.
Source digest охватывает весь документ; bundle digest — исполняемый контракт.
Stateful bundle должен также охватывать раскрытые зависимости, версии bindings
и параметры модели, prompt, tools, clock и budget. Компиляция не даёт права
приписывать проектируемым branches фактический успех.
